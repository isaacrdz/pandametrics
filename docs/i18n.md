# Internationalization (i18n)

How to add English and Spanish to Panda Metrics with next-intl (the i18n library in the project overview stack), with a language switcher in the top bar, and how to migrate every existing string.

**Product decisions** (2026-10-13):

- **URLs do not change with the language.** No `/en` or `/es` prefix.
- **The choice is stored in the browser's `localStorage`.**
- **The default language is English (`en`).**

Researched on 2026-10-13 against `main` at `c85bb32` (Next.js 16.4.0, React 19.3, `cacheComponents: true`, `partialPrefetching: true`), the next-intl docs for v4.x (context7, `/amannn/next-intl`) and `node_modules/next/dist/docs/01-app/02-guides/internationalization.md`.

## 1. Current state

- The UI is Spanish only. `src/app/layout.tsx` hardcodes `lang="es"` and the metadata in Spanish.
- Copy lives in `COPY` constants at the top of each component, plus some inline strings.
- `src/lib/format.ts` formats numbers, percentages and dates with a fixed `es-MX` locale, and builds "N respuesta(s)" by hand.
- `src/lib/date-range.ts` holds the range labels ("Últimos 30 días", …).
- `src/lib/mock-data.ts` holds reaction and rating labels ("Muy malo", "1 estrella", …), but those are **survey content** (stored in each `AnswerOption`), not UI copy.
- next-intl is not installed; there is no `messages/` folder.

## 2. Where the locale lives: `localStorage`

`localStorage` only exists in the browser. The server never knows the chosen language. That one fact drives the whole design:

| Topic | Consequence |
| ----- | ----------- |
| Server render | The server always renders the **default locale (English)**. The HTML, metadata and anything rendered by a Server Component are English |
| Translated text | Must be rendered by **Client Components** under a client-side provider that reads `localStorage`. A Server Component that renders text would stay English for Spanish users |
| Cache Components | Good news: nothing reads cookies, headers or params for the language, so there is **no runtime data**. Pages keep their static shell, no extra `<Suspense>`, no **blocking-route** warnings |
| URLs | Unchanged: `/dashboard`, `/s?code=X`. No `[locale]` segment, no `proxy.ts`, no next-intl navigation wrappers. `next/link` and `next/navigation` stay as they are. Printed QR codes are untouched |
| First paint for Spanish users | The browser paints the English HTML before React hydrates and switches to Spanish → a visible flash of English. Mitigated with an inline script (section 4) |
| Shareable links | A link never carries the language; each browser shows its own choice |
| Per device | The choice is per browser and device. On a kiosk tablet, the operator sets it once and it stays |
| Server-side text | Server Actions, route handlers, emails or server toasts cannot see `localStorage`: the client must send `locale` explicitly. The kiosk already sends `locale` with each response (overview, section 7) |
| Other tabs | The `storage` event keeps open tabs in sync when the language changes |

Alternatives that were discarded:

- **Locale in the URL** (`/en/…`, `[locale]` segment, `next/root-params`): server-rendered in the right language and fully static, but it changes the URLs. Rejected by the product decision.
- **Cookie**: the server could render the right language, but reading `cookies()` is runtime data under `cacheComponents: true`. It would make the root layout and every translated component dynamic. The requirement is `localStorage` anyway.

## 3. Locales and formatting

- Stored values in `localStorage` (key `panda-metrics:locale`): `"en"` (default) or `"es"`. Any other value or a missing key means `"en"`.
- Formatting locales: `en` → **`en-US`**, `es` → **`es-MX`**. Plain `es` changes how numbers look, so the provider receives the regional code (checked with Node 24 `Intl`):

| Value | es | es-MX | en-US |
| ----- | -- | ----- | ----- |
| `3062` | 3062 | 3,062 | 3,062 |
| `1234567` | 1.234.567 | 1,234,567 | 1,234,567 |
| `0.33` percent | 33 % | 33% | 33% |
| Full date | martes, 13 de octubre de 2026 | martes, 13 de octubre de 2026 | Tuesday, October 13, 2026 |

- Messages are per language: `src/messages/en.json`, `src/messages/es.json`.
- **Timezone is independent of the language**: `America/Mexico_City` passed explicitly to the provider (later per user / `?tz=` as the overview describes). Date ranges keep their own timezone.
- No `Accept-Language` / `navigator.language` detection: the default is always English until the user picks Spanish. Detection can be added later inside `getStoredLocale` if the team wants it.

// src/i18n/config.ts
export const LOCALES = ["en", "es"] as const;
export type AppLocale = (typeof LOCALES)[number];

export const DEFAULT_LOCALE: AppLocale = "en";
export const STORAGE_KEY = "panda-metrics:locale";
export const TIME_ZONE = "America/Mexico_City";

// Regional codes for Intl (numbers, percentages, dates)
export const INTL_LOCALES: Record<AppLocale, string> = { en: "en-US", es: "es-MX" };

export function isLocale(value: unknown): value is AppLocale {
  return LOCALES.includes(value as AppLocale);
}

```tsx
// src/i18n/LocaleProvider.tsx
"use client";

import { createContext, use, useCallback, useEffect, useSyncExternalStore } from "react";
import { NextIntlClientProvider } from "next-intl";
import en from "@/messages/en.json";
import es from "@/messages/es.json";
import { DEFAULT_LOCALE, INTL_LOCALES, STORAGE_KEY, TIME_ZONE, isLocale, type AppLocale } from "./config";

const MESSAGES = { en, es };
const CHANGE_EVENT = "panda-metrics:locale-change";

function getStoredLocale(): AppLocale {
  try {
    const value = window.localStorage.getItem(STORAGE_KEY);
    return isLocale(value) ? value : DEFAULT_LOCALE;
  } catch {
    return DEFAULT_LOCALE; // storage blocked (private mode, policies)
  }
}

function subscribe(onChange: () => void) {
  window.addEventListener("storage", onChange);      // other tabs
  window.addEventListener(CHANGE_EVENT, onChange);   // this tab
  return () => {
    window.removeEventListener("storage", onChange);
    window.removeEventListener(CHANGE_EVENT, onChange);
  };
}

const LocaleContext = createContext<{ locale: AppLocale; setLocale: (l: AppLocale) => void } | null>(null);

export function LocaleProvider({ children }: { children: React.ReactNode }) {
  // Server and hydration use the default; the client snapshot reads localStorage
  const locale = useSyncExternalStore(subscribe, getStoredLocale, () => DEFAULT_LOCALE);

  const setLocale = useCallback((next: AppLocale) => {
    try {
      window.localStorage.setItem(STORAGE_KEY, next);
    } catch {}
    window.dispatchEvent(new Event(CHANGE_EVENT));
  }, []);

  // Keep <html lang> in sync and reveal the page hidden by the inline script
  useEffect(() => {
    document.documentElement.lang = locale;
    document.documentElement.classList.remove("locale-pending");
  }, [locale]);

  return (
    <LocaleContext value={{ locale, setLocale }}>
      <NextIntlClientProvider locale={INTL_LOCALES[locale]} messages={MESSAGES[locale]} timeZone={TIME_ZONE}>
        {children}
      </NextIntlClientProvider>
    </LocaleContext>
  );
}

export function useAppLocale() {
  const context = use(LocaleContext);
  if (!context) throw new Error("useAppLocale must be used inside LocaleProvider");
  return context;
}
```

Notes:

- **Why both message files are bundled**: switching is instant with no request. About 70 strings is a few KB per language. If the catalog grows, load the non-default language with a dynamic `import()` on demand.
- **Flash of English**: only for browsers that chose Spanish. The inline script hides the body until React has applied Spanish (`locale-pending`), with a 3-second safety timeout if JavaScript fails. The trade-off is that those users see a blank page a little longer instead of English text. It is the same approach `next-themes` uses for the theme. English users (the default) see no change.
- **Hydration**: `useSyncExternalStore` hydrates with the server snapshot (`en`) and then re-renders with the stored locale. `suppressHydrationWarning` on `<html>` (already there for `next-themes`) covers the `lang` set by the script.
- **Streamed Suspense boundaries** (found during implementation): the dashboard content streams inside `<Suspense>` and can hydrate *after* the provider switched to Spanish, which causes a hydration mismatch. The implemented provider therefore remounts its children on the client (`<Fragment key>`) the first time the locale differs from the server's. English visitors never remount. `ThemeProvider` sits outside `LocaleProvider`, because it renders an inline script that must not be remounted.
- **Reveal guard**: the effect only removes `locale-pending` when the rendered locale equals the stored one. The first effect after hydration still sees `en`.
- **Blocked storage**: an in-memory fallback keeps the switch working until the next reload.
- **Plugin and `request.ts`**: they keep next-intl working in Server Components and in `generateMetadata` (always English), so a Server Component that calls `useTranslations` does not crash; it just renders English. The request config uses no cookies or headers, so it adds no runtime data.
- **Metadata**: title "Panda Metrics" is the same in both languages; the description stays in English (the server cannot know the choice). `document.title` changes are not needed now.
- **Typed keys**: `Messages: typeof en.json` makes `t("unknown")` fail `tsc`. It does not check that `es.json` has every key; add the parity check from section 8.

### Server and Client Components

Because the server only renders English, **every component that shows translated text must be a Client Component**. Server Components keep fetching data and pass it as props. Survey data with `Date` fields serializes fine to Client Components.

| Component | Today | After |
| --------- | ----- | ----- |
| `dashboard/page.tsx` | Server, renders headings and footer | Stays Server (reads `searchParams`, calls `getDashboardData`); headings, empty state and footer move to a client `DashboardSection` / `DashboardFooter` |
| `TopBar.tsx` | Server | Stays Server; the "New survey" button moves to a client `NewSurveyButton` |
| `StatCards.tsx`, `SurveyCard.tsx`, `SurveyGrid.tsx`, `CreateSurveyCallout.tsx`, `DashboardSkeleton.tsx` | Server | Add `'use client'`; props unchanged |
| `NavMain`, `NavUser`, `Greeting`, `OrganizationSwitcher`, `CollectionsToolbar`, `CopyButton`, `SurveyResults` and the charts | Client | Unchanged; use `useTranslations` / `useFormatter` |
| `AppSidebar.tsx`, `StatCard.tsx`, `EmptyState.tsx`, `MetricBar.tsx`, `ReactionFace.tsx` | Server / shared | Unchanged (no own text, or text through props from a client parent) |

This shifts the coding standard "Server Components by default" to **"Server Components fetch, Client Components render text"**. Add it to `context/coding-standars.md`. The mock data and `src/lib/dashboard.ts` stay server-only; only the computed props cross to the client.

### What is not translated

- **User content**: survey names and descriptions, question text, poll options, and the labels / colors of reaction and rating options (each `AnswerOption` stores its `label`). The mock data stays as is.
- **Names**: organization and user names.
- **Default option labels**: when the survey editor creates a Satisfaction or Rating survey, it fills the default labels from the creator's active locale (messages added in that feature) and stores them. They are never re-translated, because responses keep a snapshot of the label. Whether a survey should store its own `locale` stays an open decision for the kiosk.

## 6. Formatting

- **Remove** `formatNumber`, `formatPercent`, `formatResponses` and `formatLongDate` from `src/lib/format.ts`; keep `getInitials` and `normalizeSearch`.
- Numbers: `format.number(value)` from `useFormatter()`.
- Percentages: `format.number(share, { style: "percent", maximumFractionDigits: 0 })`, or `{share, number, percent}` inside a message.
- Counts with a noun: `t("common.responses", { count })`.
- Full date in `Greeting`: `format.dateTime(date, { dateStyle: "full" })`; it keeps `useSyncExternalStore` for the clock.
- Rating average: `format.number(average, { minimumFractionDigits: 1, maximumFractionDigits: 1 })`.
- Date ranges: `RANGE_OPTIONS` keeps only `value`s; labels from `t(\`dateRange.${key}\`)`.

## 7. Language switcher

`src/components/layout/LanguageSwitcher.tsx`, a Client Component that mirrors `OrganizationSwitcher`:

```
[ 🌐 EN ▾ ]   ┌──────────────┐
              │ Language     │
              │ English   ✓  │
              │ Español      │
              └──────────────┘
```

- **Trigger**: outline `Button`, `rounded-full`, `h-11`, `LanguagesIcon` + the active code (`EN` / `ES`, hidden below `sm` so it is icon-only on mobile), `aria-label` "Language: English" / "Idioma: Español".
- **Menu**: `DropdownMenuLabel` "Language" / "Idioma", one `DropdownMenuItem` per locale with its native name and a `lang` attribute (`lang="en"` / `lang="es"`), and a check on the active one.
- **Placement**: in `TopBar`, between `OrganizationSwitcher` and "New survey".
- **Switching**: `setLocale(next)` from `useAppLocale()`. It writes `localStorage`, notifies the provider and re-renders every translated component in place. There is **no navigation and no server request**, so the path, `?q=`, `?range=`, scroll position and open menus are kept.
- **Persistence**: `localStorage` per browser. When auth exists, `User.locale` can be saved too and copied into `localStorage` after login, so the language follows the user across devices.

## 9. Recommendation

Use next-intl **without i18n routing**:

- **Provider**: a client `LocaleProvider` reads the language from `localStorage` (`panda-metrics:locale`, default `en`) with `useSyncExternalStore`, bundles both message files and wraps the app in `NextIntlClientProvider` with `en-US` / `es-MX` for formatting.
- **Server**: it always renders English, so translated text lives in Client Components while Server Components keep fetching data.
- **First load**: an inline script in `<head>` sets `lang` and hides the page until Spanish is applied, avoiding the flash of English for Spanish users.
- **What the design keeps and gives up**: URLs, QR codes and the static shell under Cache Components stay exactly as they are. It gives up server-rendered Spanish HTML and language-specific links, which the product does not need.

Ship it as one feature in the order of section 8, with the `LanguageSwitcher` in the top bar switching languages in place.
